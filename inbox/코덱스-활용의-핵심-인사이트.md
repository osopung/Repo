# 코덱스 활용의 핵심 인사이트

## 1. 코덱스는 답변 도구가 아니라 작업 동료다

코덱스는 채팅으로 답만 주는 AI가 아니다.

- 컴퓨터에 파일을 만든다.
- 기존 파일을 읽고 수정한다.
- 코드를 작성하고 실행한다.
- 브라우저에서 결과를 확인한다.
- GitHub·Gmail·Vercel 같은 외부 도구와 연결한다.
- 프로젝트를 실제 결과물로 완성한다.

> **코덱스는 아이디어를 문서·코드·이미지·웹사이트로 바꾸는 실행형 동료다.**

## 2. 아이디어를 채팅 기록으로 끝내지 않는다

좋은 아이디어가 떠올랐을 때 일반 채팅만 하면 대화 기록으로 흘러갈 수 있다.

```text
아이디어
→ 프로젝트 폴더
→ 문서화
→ 조사와 기획
→ 결과물 제작
```

프로젝트는 단순히 코덱스 안의 공간이 아니라, 내 컴퓨터에 실제 파일이 저장되는 작업 폴더다.

## 3. `AGENTS.md`는 프로젝트 설명서다

`AGENTS.md`에는 다음 내용을 적는다.

- 프로젝트의 목적과 배경
- 작업 방향
- 중요하게 볼 기준
- 문체와 디자인 원칙
- 지켜야 할 규칙

이 파일을 만들어 두면 새 스레드에서 작업할 때마다 프로젝트를 다시 설명하지 않아도 된다.

> **`AGENTS.md`는 AI가 프로젝트의 맥락을 잊지 않도록 하는 기본 안내서다.**

처음부터 완벽하게 만들 필요는 없다.

1. 짧게 시작한다.
2. 작업하면서 방향이 바뀌면 수정한다.
3. 공식 문서나 베스트 프랙티스를 참고해 다듬는다.

## 4. 프로젝트의 문서가 다음 작업의 재료가 된다

한 번 만든 문서는 보관용으로 끝나지 않는다.

```text
시장 조사
→ 브랜드 전략
→ 비주얼 방향
→ 제품 이미지
→ 랜딩 페이지
→ 이메일
```

앞에서 만든 문서를 다음 작업의 입력으로 활용할 수 있다. 프로젝트 안의 문서는 단순한 기록이 아니라, AI가 계속 활용하는 **맥락 데이터베이스**다.

## 5. 작은 작업을 연결해 하나의 결과물로 만든다

코덱스의 강점은 서로 다른 작업을 하나의 흐름으로 연결하는 데 있다.

```text
아이디어 구상
→ 시장 조사
→ 전략 문서 작성
→ 이미지 제작
→ 팀 이메일 작성
→ 웹사이트 제작
→ 로컬 실행
→ 브라우저 검토
→ 인터넷 배포
```

각 작업을 따로 처리하는 것이 아니라, 앞 단계의 결과를 다음 단계에서 활용한다.

## 6. 작업이 커지면 먼저 계획을 세운다

간단한 작업은 바로 시켜도 되지만, 웹사이트처럼 여러 파일과 과정이 필요한 작업은 먼저 계획을 세운다.

```text
현재 폴더와 자료 확인
→ 작업 순서 계획
→ 계획 검토
→ 승인
→ 구현
```

계획 모드를 활용하면 무엇을 먼저 할지, 어떤 파일을 만들지, 어떤 자료를 참고할지, 어떤 순서로 검증할지를 먼저 확인할 수 있다.

> **큰 작업은 바로 실행하지 말고 계획부터 확인한다.**

## 7. 브라우저에서 실제 결과를 검증한다

웹페이지는 코드를 만들었다고 끝나지 않는다.

1. 개발 서버를 실행한다.
2. 브라우저에서 페이지를 연다.
3. 버튼과 입력 폼을 직접 확인한다.
4. 모바일 화면에서도 확인한다.
5. 화면의 특정 부분에 주석을 달아 수정 지시를 한다.

코덱스는 브라우저에서 직접 화면을 확인하고, 필요한 경우 스크롤·버튼·레이아웃을 점검할 수 있다.

> **코드가 맞는지보다 실제 사용 화면이 제대로 작동하는지가 중요하다.**

## 8. 이미지와 웹페이지도 반복해서 개선한다

이미지나 웹페이지를 한 번에 완성하려 하지 않는다.

```text
초안 생성
→ 부족한 점 확인
→ 바꿀 것과 유지할 것 구분
→ 수정 요청
→ 다시 확인
```

이미지 수정 지시에는 다음처럼 구분해서 말하면 좋다.

- 바꿀 것
- 유지할 것
- 배경 처리
- 추가하지 말아야 할 것
- 로고·워터마크·텍스트 제한

## 9. GitHub는 AI 작업의 안전장치다

AI가 여러 파일을 한꺼번에 수정하기 때문에 이전 상태로 돌아갈 수 있어야 한다.

- **커밋**: 현재 작업 상태를 저장
- **푸시**: 저장한 내용을 GitHub에 업로드

```text
작은 작업 완료
→ 커밋
→ 중요한 시점에 푸시
```

예:

- 아이디어 문서 작성 후 커밋
- 시장 조사 후 커밋
- 랜딩 페이지 1차 완성 후 커밋
- 배포 전 커밋과 푸시

> **GitHub는 단순 저장소가 아니라 AI와 함께 일하기 위한 복구·협업·이력 관리 장치다.**

## 10. 권한은 필요한 만큼만 허용한다

코덱스의 전체 권한을 허용하면 편리하지만, 파일 수정·터미널 실행·네트워크 사용을 자동으로 할 수 있다.

따라서:

- 작업 범위가 명확할 때만 높은 권한을 사용한다.
- 외부 서비스 연결이나 삭제·배포 작업은 내용을 확인한다.
- 무엇을 실행하는지 모를 때는 기본 승인 모드를 유지한다.

> **편리함이 커질수록 실행 범위와 권한을 확인해야 한다.**

## 11. 외부 도구를 연결하면 업무 흐름이 확장된다

Gmail, GitHub, Vercel 같은 플러그인을 연결하면 코덱스 안에서 다음을 이어서 할 수 있다.

- 프로젝트 자료를 바탕으로 이메일 초안 작성
- 팀원에게 보낼 메일 생성
- GitHub에 저장·공유
- 웹사이트 배포
- 배포된 결과 확인

```text
내 컴퓨터의 파일
+ 웹 자료
+ 외부 업무 도구
= 하나의 연결된 작업 흐름
```

단, 이메일 전송이나 외부 공개는 반드시 최종 확인 후 실행한다.

## 12. 코덱스에게 공부도 시킬 수 있다

모르는 개념이 나오면 코덱스에게 물어볼 수 있다.

- AGENTS.md를 초보자에게 설명해 줘.
- Git 커밋과 푸시의 차이를 알려 줘.
- 계획 모드는 언제 사용하는가?
- Next.js를 이 프로젝트에 왜 쓰는가?
- 공식 문서를 기준으로 스킬을 설명해 줘.
- 초등학생도 이해할 수 있게 다시 설명해 줘.

> **코덱스는 작업자이면서 개인 맞춤형 교사이기도 하다.**

## 오소풍님에게 적용할 핵심

오소풍님이 ETF 대시보드에서 사용한 방식은 다음과 같다.

```text
목적 설정
→ 설계
→ 승인
→ 작은 단계 구현
→ 테스트
→ 화면 확인
→ 수정
→ 커밋·푸시
```

앞으로 추가할 핵심은 세 가지다.

1. 프로젝트 초기에 `AGENTS.md`를 만든다.
2. 큰 작업은 계획 모드에서 먼저 계획을 확인한다.
3. 문서·이미지·코드·화면을 하나의 프로젝트 폴더 안에서 연결한다.

## 한 줄 정리

> **코덱스를 잘 쓰는 사람은 AI에게 질문만 하는 사람이 아니라, 프로젝트 폴더·맥락 문서·검증 절차·Git 기록을 갖추고 아이디어를 실제 결과물까지 연결하는 사람이다.**
